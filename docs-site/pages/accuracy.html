How it was measured

Each system ran a 40-minute "day": a night trough, a morning ramp, a lunch peak, a three-minute push above capacity, an evening decline. The model was calibrated on that run only. Then it predicted runs it never saw (the runs, not the method: several calibration rules were added after one of these predictions missed, so treat the table as in-sample for the method, and each check as a single run):

  • the same day with a change really applied (a second replica, an autoscaler, a bigger instance);
  • step load tests up to the breaking point, as built and with the change.

The telemetry was recorded like production: an OpenTelemetry Collector writing 20% of traces and turning every span into request metrics, container metrics scraped by Prometheus every 5 seconds, k6 sending Poisson arrivals and keeping every request. The bill is an AWS Cost and Usage Report built from what actually ran, priced as Fargate in us-east-1.

Where it misses

Each model is also calibrated on the first 70% of its history and asked to predict the rest. Cost holds (0.3–6.3% off). p99 misses badly, by 72–99%, because each history ends with its push above capacity: the last 30% contains an overload the first 70% never came near. With no evidence of where the limit is, the model predicts a healthy evening. A model is only as good as the loads its history has seen, which is why every component's notes say when its capacity is an extrapolation.

On Kubernetes, with a real traffic curve

The Astronomy Shop ran on a kind cluster, observed the way production clusters are: kube-prometheus-stack, ingress-nginx, span metrics and Jaeger. It is a kind cluster on one laptop, not a managed cluster. k6 replayed the arrival curve of two days of NASA's 1995 web log, each compressed into 40 minutes: an ordinary day and the STS-70 launch day at 2.2× the traffic. Five changes to its frontend were answered by verify_change before the day, then made for real. The first version got 2 verdicts right from the ordinary day alone, called 1 inconclusive and got 2 wrong. A plain CPU-ratio rule got 4 right. The misses had one cause. A single-threaded service under a CPU limit collapses well below the limit because of CFS throttling, and extrapolating CPU per request reads that as more capacity than there is. Calibration now fits the share of throttled periods against CPU use and caps capacity where it reaches 25%, the threshold of the CPUThrottlingHigh alert. With that, the ordinary day alone got all 5 right; since a memory-leak term was added it gets 4. That score is in-sample: the throttle rules were designed on these runs.

Out of sample, verdicts on nine more runs were committed to the repository before each run was recorded, in three rounds. Across all of them the model got 3 right, 1 wrong, and said inconclusive on 5 (3 of those leaned the right way). A plain CPU-ratio rule got 6 right and 3 wrong. The model is wrong less often because it abstains more: on hit rate alone it does not beat the rule. Its p99 on each day's own traffic is within 20% of the measured p99 in only 3 of 14 runs; it underestimates busy days. In round 1 it got 3 of 4 right with none wrong, where the rule called a run that failed safe. Under a CPU limit below one core, every endpoint's p99 carries one CFS stall of (1 − limit) × 100 ms, a wait the traces cannot see. The model now takes it out of the baseline and puts it back at the plan's limit. At 1 core its p99 went from 98 to 46 ms, measured 28 (that term was designed on this run). Busy days are still underestimated, because stalls stack once more periods are throttled.

Then a node was stopped for real at minute 19 of the ordinary day. check_node_loss, run afterwards with today's code and the pod placement at the kill (a retrodiction, not a committed prediction), names the seven services that lost their only replica and gives +7 minutes out of SLO. Kubernetes replaced the pods in 348 s, against the 380 s the model allows. The measured outage was still +10.5 minutes: the frontend's gRPC channel to cart stayed broken until the frontend ran out of heap and restarted. The replay times the platform's recovery, not the clients'. The full study, with every run, is in reference/k8s/README.md.

On real production telemetry

On the busiest services in Alibaba's 2021 microservices trace (44 with enough data), the calibration predicted each service's CPU from its traffic over 3.6 held-out hours. When traffic moved by 15% or more within an hour, it was off by 5.9%, against 11.0% for CPU per request held constant and 13.2% for "the same as an hour ago". Above anything the training saw, it was off by 12.9% against 30.4%. Over all minutes, moving or not, it ties "the same as an hour ago" (7.4% each). Details: reference/alibaba/README.md.

Where you see it

The accuracy record travels with the model: the backtest screen's Model accuracy panel, hindcast accuracy model.json, the footer of every report, pull-request comment and card. For your own data, hindcast calibrate --holdout 0.3 adds the same holdout check.
