For AI agents

Let your agent check an infrastructure change against last week's production before it proposes it. It connects to your telemetry, builds the model and reads its trust report, then answers with a verdict, the money, the SLO minutes and how far to trust them.

What the agent does

connect_telemetry  →  collect_telemetry  →  calibrate_model  →  verify_change
probe Prometheus,     history into the       the model, and      verdict, confidence,
Jaeger or Tempo       workspace              how far to trust it $, SLO minutes, why

Your agent (Claude Code, Cursor, Claude Desktop, or anything with a shell) gets eleven tools over MCP or as hindcast agent <tool> with JSON in and out. The user asks "can we move checkout to Graviton?". The agent finds the Prometheus and Jaeger, collects a week of history, fits the model, backtests the change and answers with evidence.

Everything is read-only towards your systems: queries to your Prometheus and Jaeger or Tempo, and one kubectl get against a context you name. Credentials stay in environment variables. Hindcast itself sends nothing anywhere; what the tools return goes to your agent's model provider, as with any tool.

Or one command

hindcast quickstart --prometheus http://localhost:9090 --jaeger http://localhost:16686 --last 24h

Connects, collects, calibrates and writes the capacity review, showing each step and its time; on the reference cluster it takes about 20 seconds. The review opens with five lines a lead can read: whether the recorded day held its SLO and whether 1.5× and 2× days would, the headroom, the cost (with what a commitment saves), the one change that passed its backtest, and how many services the model fits. Then the commands to run next. --jaeger is optional (see without traces).

Set up

npm run sim -- agent setup                 # proves the server starts, prints every host's config
npm run sim -- agent setup cursor --write  # or claude, vscode, desktop, windsurf: merges it into that host's file

Setup fills in the absolute paths, keeps any other servers in the file, and completes an MCP handshake with the server before it says it worked. By hand: npm run cli:build, then claude mcp add hindcast -- /path/to/hindcast/engine-rs/target/release/hindcast mcp; other hosts take the same command in their mcpServers config (examples/agents/mcp.json). For agents without MCP: hindcast agent connect_telemetry '{…}'; examples/agents/AGENTS.md is an instruction file to paste into your project. For Claude Code there is also a skill, examples/agents/skills/verify-infra-change.

The tools

toolwhat it does
connect_telemetryprobes Prometheus (which metric presets exist, which services, when traffic flowed) and Jaeger or Tempo (services, which ones requests enter through, load generators to ignore). Maps container names onto service names. Says what is missing.
collect_telemetryqueries a window (last: "7d"), fetches traces spread across it, adds the bill, imports. Reports per service which signals exist.
calibrate_modelfits the model and holds back 30% of the history to measure accuracy. Returns a trust report: services whose limit the history reached, services whose capacity is extrapolated, services it can't explain.
verify_changebacktests changes given as a strategy, a Kubernetes manifest diff, a Terraform plan, or edited manifests against the live cluster. Verdict, confidence, $ with its band, SLO minutes, worst moment, headroom, an HTML report, and a link that opens the result on the backtest screen.
suggest_changes"what should we change?": fixes for the services that ran out of capacity (more replicas, of the host for an in-process dependency; more CPU or autoscaling when CPU-bound) and savings for the ones that idled (fewer replicas, smaller CPU, Graviton). All backtested and judged; the passing savings are also tried together. With traffic it answers for a busier day (launch day, Black Friday), and a service that leaks gets memory and replica fixes. On the live HotROD: six savings, together −$35/month with no SLO change, and two customer replicas cutting failed requests by 79%.
review_capacitythe capacity review in one call: headroom, 1.5× and 2× traffic, a node lost at the peak, limits that bind (CPU quota, memory, leaks), the node pool, how much to commit to (the floor the history always ran, priced at 1- and 3-year rates), and the fixes and savings that pass.
find_headroomreq/s within SLO, as built and with a change, and what binds first.
verify_designa design on paper: failures, headroom, cost against a budget; fixes as exact spec changes, so the agent can loop until it passes.
read_clusterkubectl get deployments,statefulsets,hpa on a named context, saved as the base for edited manifests.
model_statuswhat the workspace already holds, and the next step.

Verdict and confidence

Every result has both. The verdict is about the history; the confidence is about the model.

when
failthe change adds more than half a minute out of SLO over the window, or fails more requests than the SLO's whole error budget over the window (1% of its requests at a 1% SLO), beyond what failed as built (median of 30 capacity draws)
inconclusivethe median passes but the worst 10% of draws don't; or confidence is low; or the change cuts headroom below traffic the system has already seen
passotherwise
confidence lowa service the change depends on fits poorly, or the change runs it at ≥ 80% of a capacity the history never came near
confidence mediumit runs past the history's peak, a touched service fits only fairly, the model missed an accuracy check, or the history is under a day

A pass at low confidence is not "safe": the backtest found no problem on capacities the history never tested. Agents are told to say so and recommend a load test.

Cost comes with its basis: your bill, or list price (AWS Fargate on-demand, from CPU and memory limits) when there is no bill.

Tested end to end

Live, against the reference HotROD (four Go services and a mutex-guarded simulated MySQL) under a 30-minute "production day". Its telemetry went through an OpenTelemetry Collector into Prometheus and Jaeger. Headless Claude Code got only this, and only the Hindcast tools:

Our Prometheus is at http://localhost:9090 and Jaeger at http://localhost:16686. SLO: p99 under 1 s, under 3% errors; clients time out after 5 s. Use the last hour. Can we move all our services to Graviton without hurting reliability, and would letting clients retry failed requests twice (no retry budget) make things better or worse?

One run, 17 turns, 2.5 minutes (the session transcript is not in the repository; scripts/agent-e2e.mjs below repeats the flow and can be rerun):

  1. It connected and collected. The coverage report flagged services in no trace (a second system sharing the Prometheus) and traced services with no container. The agent checked, then connected again with exclude for the other system and hostedBy for the in-process mysql and redis.
  2. Calibrated: the mysql lock at 9.1 req/s (band 7.6–10.6). A stress test of the same build measured 9.9.
  3. Verified both changes, and on its own initiative a third: Graviton with 20% slower cores.
changeverdictwhat it said
Everything on Gravitoninconclusive, low confidencesaves $16.29/month (list prices) with no change in SLO minutes, even at 20% slower cores: the bottleneck is a lock, not CPU. One hour of history and a poorly fitted lock: migrate one service or load-test first.
Clients retry twice, no budgetfail+6 minutes out of SLO (+5.5 … +6.5), +1,241 failed requests. The failures are queue timeouts, so retries join the same full queue. Try two customer replicas or a retry budget instead.

The same flow runs as a script through a real MCP client (scripts/agent-e2e.mjs): connect 2.7 s, collect 4.5 s (1,682 traces from Jaeger), calibrate 8 s, verify under a second. Through Tempo instead of Jaeger it found the same services and call edges, fetched 509 traces and calibrated the mysql lock at 10.2 req/s.

What your telemetry needs

signalfrom
requests, errors, latencyOpenTelemetry Collector span metrics, or OpenTelemetry HTTP server metrics, in any Prometheus-compatible store (Prometheus, Thanos, Mimir, VictoriaMetrics); or Datadog APM trace metrics (trace.<span>.hits, .errors, the trace.<span> latency distribution) through --datadog <site>
requests, errors, latency at the edgeingress-nginx (takes precedence over span metrics for the entry service); in Datadog, nginx_ingress.controller.requests (requests and errors only)
CPU, limits, replicascAdvisor, or kubelet + kube-state-metrics, grouped by Deployment/StatefulSet/DaemonSet and kept to the system's namespaces; in Datadog, the Agent's kubernetes.cpu.*, kubernetes.memory.*, kubernetes.cpu.cfs.* and kubernetes_state.*.replicas_* by kube_deployment/kube_stateful_set
topology and self timeJaeger or Tempo, or OTLP / Jaeger JSON files; without traces, Istio or Linkerd metrics, the OpenTelemetry service graph, span metrics, Datadog's APM service dependencies (callers and callees, not counts), or a topology file
costan AWS CUR or GCP billing export; list prices otherwise

Without traces

Traces are optional. hindcast quickstart --prometheus <url> alone gives a review: who calls whom is read from Istio's or Linkerd's caller → callee counters, the OpenTelemetry service graph, span metrics' client spans matched to the servers that answer them, or a topology file (--topology); ingress-nginx names the entries. What is lost is said in the review's Trust line, e.g. No traces: topology from istio metrics; no per-endpoint latency. Endpoints of a service share one path, self time is a service's latency less its calls' time, and a service with no latency metric gets its capacity from CPU alone, to its throttling knee.

On the reference kind cluster, the same day read both ways: span metrics found 11 of the 27 traced call edges (all the gRPC ones), calls per frontend request were close (product-catalog 1.52 against 1.32 traced), and seven services' capacities matched within a few percent. The frontend came out at 162 req/s per replica from CPU against 307 from traces; the recorded runs, where one replica failed at a 180 req/s peak, side with the lower number, though that is an inference, not a measurement. Headroom was 460 req/s against 500 and 778 for two trace samples; those traced figures predate a fix to how a replicated entry service's endpoint mix is read (its replicas' counters merged into one series), which on a later window moved traced headroom from 411 to 605 req/s with capacities unchanged. With the collector's peer labels (server.address, peer.service) and service graph turned on, a later live window gave span metrics 14 of the 15 traced edges and the service graph 13; the service graph's calls per request came within 4% of what each service served, span metrics 12–15% low for two services (reference/k8s/README.md, "Without traces, live"). Linkerd and Istio are tested only against mock Prometheus servers so far; there is no mesh on the reference cluster.

Datadog: hindcast quickstart --datadog datadoghq.com reads the keys from DD_API_KEY and DD_APP_KEY (or the variables --dd-api-key-env and --dd-app-key-env name; the keys are never written anywhere) and queries the public Metrics API, read-only. Compared with Prometheus and traces it loses call counts (service dependencies name only who calls whom), nodes, pods per node and autoscalers, and p99 where there is no latency distribution. It is tested against a mock server built from Datadog's API documentation; no live Datadog account was used.
