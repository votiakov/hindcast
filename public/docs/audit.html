Failure audit and analysis

What breaks first, and what it costs. The audit replays every way production goes wrong, grades each by what users would have seen, and verifies and prices each fix.

The failure audit

The default design: one API server, one Postgres.

  1. Load and the price of an outage

    The expected load, and what a minute of outage costs you. With a price, every risk gets a dollar figure.

  2. The score

    The share of incidents survived, weighted by severity. 24/100 here.

  3. The headline numbers

    Incidents survived, headroom (breaking point ÷ expected load) and what first breaks, and what the design costs per month.

  4. The load curve

    Latency as load rises past today's: where it crosses the SLO is the breaking point, with the cost per million requests now and at the limit.

  5. The risk register

    One row per incident, worst first: every component dying, every dependency turning slow or failing 20% of requests, caches restarting cold, zones going dark, a 3× surge, a ramp past the breaking point. Each is graded critical, major, minor or ok, with its blast radius and recovery time.

  6. Replay on the board

    Plays the incident live from a clean start.

  7. Studio clip

    The incident as a clip: this design against the fixed one, same incident.

  8. Verified fixes

    Candidate fixes (another instance, a load balancer, a replica, a standby, timeouts and breakers, retry budgets, autoscaling) are each tested by re-running the same incident on the changed design, and priced per month. Fixes that don't help are dropped. Apply applies one (undoable). Backtest replays it over real history when the board came from a backtest.

  9. The report

    Markdown to paste, or a self-contained HTML page for a design review.

  10. Risks on the board

    Components that take the system down alone are marked "single point of failure".

From the command line, bottleneck audit arch.yaml --rps 500 --cost-per-min 1000 --md report.md exits with code 2 on a critical finding, so it can gate a pull request that changes an architecture spec.

Analysis

The discrete-event engine: every request simulated, so tails, retry storms and breaker oscillation emerge rather than being approximated.

  1. Monte Carlo

    Many seeded runs of the current traffic (optionally killing the busiest server halfway): p50, p99, p99.9, errors and cost with 95% confidence intervals, and the share of runs that meet the SLO.

  2. Breaking point

    The most req/s it serves within the SLO, and the component that limits it.

  3. Cheapest config meeting the SLO

    The optimizer resizes everything to the cheapest design that still meets the SLO, optionally changing language runtimes; Apply to board takes it.
