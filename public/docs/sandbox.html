Design simulator

Sandbox

Build any system, push traffic and failures through it, and watch where it gives out. Every run is recorded, so you can rewind the whole board.

The board

  1. Components

    Users, DNS, CDN, Load Balancer, API Gateway, API Server, Worker, Serverless Fn, Cache, Database, Read Replica, Key-Value Store, Object Storage, Queue, Stream, GPU Inference, LLM Provider API, Third-party API. Drag onto the board or click; connect right handle to left handle. ⌘C ⌘V ⌘D copy, paste and duplicate (the links between copies come along); Shift-drag selects several; N adds a note. With a component selected, a click adds the next one linked from it, and a cache or CDN goes between it and what it calls, so it has an origin. The size on a card (S, M, L) explains itself on hover.

    Sections. Select a few components and press Group as section (or G): a dotted frame with a plain label, to say what a part of the design is for (“checkout path”). Double-click the label to rename it; drag the label or the edge to move what is inside; the frame fits its components as they move. A section is not a zone: it fails nothing and the simulation ignores it. Zones are solid frames with a zone chip. Sections are kept in the YAML, share links, copy and paste, PNG and SVG, and are drawn as dotted subgraphs in the Mermaid export.

  2. A component, live

    Load in, dropped, capacity, CPU and instances. Its edge and status turn red when it saturates.

  3. Requests flowing

    Each connection shows its rate. Particles turn red where requests fail.

  4. What users see

    Throughput, error rate, p99, cost. Click for the cost breakdown per component and per cloud (on demand, or with a 1- or 3-year commitment from Settings), $ per million requests, where requests fail (each component dropping requests, and why, with trace to follow a request through it on the board), where the time goes (each component’s own time per request, and the network’s), a request, hop by hop (one sampled request's network, queue and service time at each component, failures and cache hits drawn at their rates) and the error-budget burn rate.

  5. Design

    Save (⌘S), open, save a copy, download YAML, download the board as PNG or SVG, copy it as a Mermaid diagram, share a link, embed code, a new blank design — and templates: the lessons’ boards, every comparison’s two sides, and seven real systems (chat, video, ride dispatch, payments, timelines, an AI assistant with retrieval, e-commerce search) rebuilt from their engineers’ public write-ups.

  6. Architecture as code

    The design as YAML, synced with the board both ways.

  7. Failure audit

    What breaks first, and what it costs. See failure audit.

  8. Analysis

    Monte Carlo with confidence intervals and why requests failed (where each failure started: overloaded, out of threads, rate limited, timed out, a cut link…), breaking point, cheapest sizing.

  9. Rewind

    Every run is recorded. Drag to rewind the whole board to any moment; ←/→ steps. copy timeline gives the run as an incident timeline in Markdown.

  10. Traffic

    Requests per second, the share of reads, and the pattern: steady, day/night, spiky or a ramp. Drop a CSV of real traffic (time, req/s) on the board to replay it. A Users component can also be a scheduled job (a cron, a nightly export): a batch every so often that competes with the users without counting as them.

  11. Chaos

    Spike ×3, kill a server, kill the database, heal everything. More per component; select a link to cut it or slow it.

  12. Minimap

    Where you are on a large board.

Everything a component can do

Select a component and its card opens up: the controls are inside it, not floating over the board. The board pans to show all of it.

  1. Instances

    Add or remove; the load balances across them.

  2. Size

    S, M or L: capacity, latency and price per instance. Exact numbers per kind in the component catalogue.

  3. Autoscale

    Target tracking with a maximum and a warm-up: "k8s pod 5–20 s · Fargate 30–60 s · EC2 ASG 90–180 s".

  4. Runtime

    Node.js, Python, Java, Go or Rust. Changes throughput per instance, latency, cold starts and the serverless bill.

  5. Resilience

    Opens the settings below; it opens by itself when any of them is set.

  6. Retries

    Per failed call: immediate, with backoff, or with a budget.

  7. Circuit breaker

    Stop calling a failing dependency for a while, with an optional degraded fallback. Servers and workers can also hold a thread per request (Tomcat-style: a slow dependency then starves everything) with a bulkhead per dependency, which refuses a call at once or lets it wait for a slot (the wait holds the thread). Queues take a redrive policy (failed messages retried, then dead-lettered); balancers and gateways a connection limit (websockets, streamed answers) and a burst.

  8. Routing

    How calls spread over what it connects to: split, fan-out to all, or failover.

  9. Fan-out

    Scatter-gather: each call goes to N partitions and waits for the slowest. The tail at scale, made visible.

  10. Queue

    A bounded queue: how many seconds of work it holds before it sheds load.

  11. Break it

    kill, or a gray failure: 10% or 50% errors, +100, +500 or +2000 ms, half capacity, flush the cache, restore.

  12. Calibrate

    From your production numbers: one instance served R req/s at C% CPU with a p50 of L ms and costs $/h. Capacity, latency and price follow.

Kind-specific settings appear on the kinds that have them: client timeouts on Users, hit rates on caches, rate limits on gateways and model APIs, continuous batching on GPUs. In the Neon and Transit themes the same controls float above the selected component.

Follow one request

Select a component and press trace in its card, or trace beside a component under where requests fail in the metrics. The board runs itself as it is now (its traffic, and whatever is killed, broken or cut) for 12 seconds in the discrete-event engine, follows a sample of requests hop by hop, and draws one that went through that component. Select another component and the board follows a request through that one instead. Esc stops. The same lines from a shell: hindcast simulate arch.yaml --engine des --trace db --failed; for an agent, the trace_request tool.

  1. The path, as text

    Each hop's time: a thin arrow is the network and the component's own work; a double one, in amber, is a request that waited in the queue for a worker first. A retry, a fan-out part or a failover target branches below the hop that made it.

  2. Where it failed

    The engine's own reason, at the component where the failure started: overloaded, down, circuit breaker open, connection refused… or timeout with the caller's deadline, on the hop the request was stuck at when the caller gave up. Components that only passed the failure on are not marked.

  3. On the links

    The links the request took are lit, with each hop's queue wait and time; a retry over the same link is counted on it. The rest of the board steps back.

  4. Another request

    Up to 12 sampled requests through each component, oldest first.

  5. Failed only

    On by default when any of them failed; off for the full sample.

  6. The run

    When the request began in the run, the load, and how many of the followed requests went through the component and failed. Change the board and it says so: run again samples the board as it is now. Tracing does not change the run: the same seed gives the same results with or without it.

Architecture as code

  1. The design as YAML

    Type here and the board follows; change the board and the YAML follows. Components, connections, zones, scenarios, variants.

  2. Checked as you type

    Schema errors and lint warnings inline. A valid spec is the same file the CLI and the MCP server take.

Drop a spec, Kubernetes manifests or terraform show -json output on the board to open it; imports list the assumptions they made.

⌘K, everything by name

  1. Type anything

    A command, a component, a design, a template, a lesson, a comparison, a chaos action. A number sets the traffic.

  2. Grouped results

    Enter runs, ↑↓ chooses, Esc closes.
