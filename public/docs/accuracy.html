Accuracy

How well the backtest predicts reality, measured on three open demo systems run under load in Docker, with their telemetry recorded the way production records it.

How it was measured

Each system ran a 40-minute "day": a night trough, a morning ramp, a lunch peak, a three-minute push above capacity, an evening decline. The model was calibrated on that run only. Then it predicted runs it never saw:

  • the same day with a change really applied (a second replica, an autoscaler, a bigger instance);
  • step load tests up to the breaking point, as built and with the change.

The telemetry was recorded like production: an OpenTelemetry Collector writing 20% of traces and turning every span into request metrics, container metrics scraped by Prometheus every 5 seconds, k6 sending Poisson arrivals and keeping every request. The bill is an AWS Cost and Usage Report built from what actually ran, priced as Fargate in us-east-1.

Where it misses

Each model is also calibrated on the first 70% of its history and asked to predict the rest. Cost holds (0.3–6.3% off). p99 misses badly, by 72–99%, because each history ends with its push above capacity: the last 30% contains an overload the first 70% never came near. With no evidence of where the limit is, the model predicts a healthy evening. A model is only as good as the loads its history has seen, which is why every component's notes say when its capacity is an extrapolation.

On Kubernetes, with real traffic

The Astronomy Shop ran on a kind cluster, observed the way production clusters are: kube-prometheus-stack, ingress-nginx, span metrics and Jaeger. It served two real days of NASA's 1995 web log, an ordinary day and the STS-70 launch day at 2.2× the traffic. Five changes to its frontend were answered by verify_change before the day, then made for real. The first version got 2 verdicts right from the ordinary day alone, called 1 inconclusive and got 2 wrong. A plain CPU-ratio rule got 4 right. The misses had one cause. A single-threaded service under a CPU limit collapses well below the limit because of CFS throttling, and extrapolating CPU per request reads that as more capacity than there is. Calibration now fits the share of throttled periods against CPU use and caps capacity where it reaches 25%, the threshold of the CPUThrottlingHigh alert. With that, the ordinary day alone gets all 5 right. That score is in-sample: the throttle rules were designed on these runs. Every p99 still misses (by 47–98%), because the queueing model has no term for time spent waiting out a throttled period. The full study, with every run, is in reference/k8s/README.md.

On real production telemetry

On 60 of the busiest services in Alibaba's 2021 microservices trace, the calibration predicted each service's CPU from its traffic over 3.6 held-out hours. When traffic moved by 15% or more within an hour, it was off by 5.9%, against 11.0% for CPU per request held constant and 13.2% for "the same as an hour ago". Above anything the training saw, it was off by 12.9% against 30.4%. Details: reference/alibaba/README.md.

Where you see it

The accuracy record travels with the model: the backtest screen's Model accuracy panel, bottleneck accuracy model.json, the footer of every report, pull-request comment and card. For your own data, bottleneck calibrate --holdout 0.3 adds the same holdout check.
